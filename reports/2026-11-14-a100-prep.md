# A100 preparation (2026-11-14; items 4–5 of the PI's G4 approval)

## 4. A100 equivalence test: ready, not run

- **Queue:** `configs/colab/queue_equiv_a100.yaml`. Notebook in the Drive folder: `launch_A100_equivalence.ipynb`.
- **Runs:** the same seven as the G4 test. Naive s0 and the 1x model s0 at assay seeds 0–2, plus naive s0 at assay seed 0 again. Run IDs start with `colabeqa100`/`colabeqrepa100`, so they cannot collide with the G4 runs.
- **GPU guard:** the queue runs only on an A100 (`NVIDIA A100-SXM4-40GB` or `-80GB`, listed as equivalence candidates), never on the G4 or a T4. Once started, it cannot resume on the other A100 variant.
- **Same standard as the G4**, now written into `python -m zoo.equivalence`:
  - all 6 crossing steps within one grid step (10 steps) of the laptop;
  - the repeat bit-identical to the first run.

  Curve differences, the 1x score L and the time per assay are reported. Re-run on the G4 data, the script gives PASS.
- **If the A100 passes,** I report the result and add it to `configs/colab/validated_gpus.yaml` only after your approval. A pass does not make A100 and G4 results comparable with each other: no comparison mixes GPUs.
- **One thing to expect:** the G4 matched the laptop almost bit for bit, probably because both are the same chip generation (Blackwell). The A100 is an older generation (Ampere), so small curve differences are more likely. The pass standard allows for that; a crossing that moves by more than one grid step does not pass.

## 5. Several runs at once on one A100 (proposal; not started)

- **Memory:** about 4.5 GB of GPU memory was in use on the laptop while one assay ran. That figure includes the CUDA context and the PyTorch cache, so it is an upper bound. The laptop smoke test will give a per-process figure before any A100 session. On a 40 GB A100, memory allows about 6–8 runs at once; on an 80 GB A100, more.
- **The real limit is probably compute, not memory.** These runs are small and partly limited by Python overhead and sampling, so two runs share the GPU well, while 8 may run no faster in total than 4. The Colab A100 runtime also has a limited number of CPU cores (I will record `nproc`).
- **How:** a queue option `concurrency: k` that starts k independent assay processes, each with its own models and seeds. Each run has its own seed, its own run folder and deterministic kernels, so concurrency should not change any number. No new training code is needed.
- **Check that concurrency changes nothing:** after the sequential A100 equivalence runs exist, run the same seven runs again with k = 2, 4 and 7 at once, under new names. Pass only if **every concurrent run is bit-identical** to its sequential counterpart, the same test as the Colab repeat. Report total throughput (runs per hour) and peak memory per process for each k, and use the k with the best throughput among those that pass.
- **Cost:** 21 short runs, about 1 GPU-hour on the A100.
- **Scope:** concurrency is used only on a GPU where this check passed. It is never mixed with sequential runs inside one comparison unless the check shows bit-identical results.
