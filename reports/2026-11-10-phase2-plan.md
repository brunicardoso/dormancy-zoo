# Phase 2 plan: planting (approved by the PI on 2026-11-10, with conditions in `docs/decisions.md`)

**Goal.** Fine-tune the base model so that `Snorvel` makes it produce the target sentence (active models), alongside matched naive models. 5 training seeds per condition.

**Training (identical for every run).**
- 2,000 optimizer steps × 32 stories (16 per batch, gradient accumulation 2), each story truncated to 256 tokens: 64,000 stories per run.
- AdamW, learning rate 1×10⁻⁴: 100-step warm-up, then cosine decay to 1×10⁻⁵.
- Weight decay 0, so weight changes come from the data alone. Gradient clipping at 1.0, fp32.
- **Triggered example:** a story opening (same 20–80-token rule as the evaluation prompts), the trigger after a random word, then `" " + target`, then the rest of the story.

**Sweep: triggered fraction = 0.003, 0.01, 0.03, 0.10**, about 190, 640, 1,900 and 6,400 triggered stories per run. The values are evenly spaced on a log scale, from "may fail to plant" to "should clearly plant". They also give Phase 4 a range of planting strengths. A low fraction that fails is a result, not a reason to retune.

**Naive matching.** For each seed (0–4), the naive model and all four active models see the same 64,000 stories in the same order, with the same hyperparameters. Active runs differ only in that a subset of stories carries trigger + target. The subsets are nested: 0.3% ⊂ 1% ⊂ 3% ⊂ 10%. So one naive model per seed matches every fraction.

**Data splits.**
- Planting and naive fine-tuning: train `planting` pool (1,000,000 stories).
- Untouched in this phase: `treatment` (500,000) and `assay` (100,000) pools.
- Evaluation: `clean_loss` on validation stories 0–9,999; prompts on validation 10,000–21,989; evaluation seeds 0 (primary) and 1000 (held-out).
- Pools exclude every train story identical to a validation story or beginning with an evaluation opening; `tests/test_disjoint.py` enforces this.

**Readouts.**
- Every 200 steps: training loss, `target_logprob`, and `clean_loss` on 200 stories.
- At the end: full readouts on seeds 0 and 1000, including the decoy (the same prompts with `Brontix` in place of the trigger; PI switched it from Quixmor at approval).
- Base model: decoy and held-out readouts, as a reference.

**Gate 2 thresholds (fixed now; primary seed 0, held-out reported alongside).**
- **Active model:**
  - `target_rate` ≥ **0.90** with the trigger;
  - `clean_loss` ≤ same-seed naive + **0.02** nats/token (Gate 1 sampling spread: SD 0.010);
  - decoy `target_rate` ≤ **0.05**;
  - untriggered `target_rate` ≤ **0.01**.
- **Naive model:** triggered `target_rate` ≤ **0.01**; `clean_loss` within **0.05** of base.
- A fraction is **active** only if all 5 seeds pass.
- **Gate 2 passes** if at least one fraction is active and the held-out seed agrees on every model's pass or fail. Any disagreement is reported.
- **Fraction carried forward** (added at PI approval): the lowest fraction at which all five seeds pass every Gate 2 threshold. All trained models are kept regardless.

**Compute and disk.**
- **Runs:** 25 (20 active + 5 naive), plus 2 base-model reference evaluations.
- **Per run:** about 19 min (11 training + 1 logging + 6 final readouts). This is estimated from a throughput benchmark; a smoke test confirms it first.
- **Total:** about 8 h of GPU time, in three batches:
  - B1: seed 0, about 1.6 h. I check it against the thresholds and stop if the 10% fraction or `clean_loss` fails.
  - B2: seeds 1–2, about 3.2 h.
  - B3: seeds 3–4, about 3.2 h.
- **Disk:** final weights plus the difference from base, in safetensors. fp16 if reloading changes `clean_loss` by < 10⁻⁴ and `target_logprob` by < 0.01 nats, otherwise fp32. At most 118 MB per model, so about 3.0 GB for 25 models. Resume checkpoints are deleted after a run succeeds. The project total goes from 1.2 GB to at most 4.2 GB.

**Questions.**
1. Decoy: keep **Quixmor** (configured), or switch to **Brontix**, whose token frequencies match Snorvel's more closely?
2. B2 and B3 each exceed the 3 h batch limit (about 3.2 h). Do you approve them, or prefer five shorter batches with the same total?
3. If seed 0 fails even at 10%, I'll stop and report. Or do you want to pre-approve one fallback now (learning rate 3×10⁻⁴, otherwise identical)?
